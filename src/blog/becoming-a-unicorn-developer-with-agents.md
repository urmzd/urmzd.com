One thing in my career that has often helped me progress quickly no matter where I'm at is leveraging all the tooling I can to enable myself, and then subsequently building tooling that enables others. One thing I learned early on from the many mentors I've had the pleasure of working with is that good developers get shit done, and great developers help others get shit done.

## The thesis

**The unicorn isn't the developer who ships more. It's the one who optimizes the workflow that ships.**

The collaborative nature of engineering has been shifting away from direct tool enablement, and agents accelerate that shift rather than reversing it. The leverage is no longer in the code you write. It's in the loop: how work gets specified, handed off, verified, and fed back. Optimize the loop and every run of it gets cheaper, including the runs you aren't present for.

Which means "others" now has two populations in it. The tooling you build has to serve the human who reads it *and* the agent that executes against it. A README that only a person can act on is half-built. So is a skill only an agent can parse.

## What still needs writing

- **The shift, concretely.** What tool enablement used to look like (shared scripts, internal CLIs, paved paths) versus what it looks like when the consumer is an agent. Same instinct, different reader.
- **The dual-audience rule.** Docs, skills, and CLIs that work for both. Tie to the skills-as-docs philosophy: the thing that teaches the agent is the same thing that onboards the human.
- **One concrete example from real work.** Pick a tool where building it for the agent made it better for people too. A number would carry this section.
- **The anti-pattern.** Individual velocity that doesn't compound. The developer who is fast with agents but leaves behind nothing another person or run can reuse is not a unicorn, just briefly expensive.
- **The leverage / decision test.** Something like: if this task arrived ten more times, would my output make run eleven cheaper? If not, you did the work instead of building the thing that does the work.
